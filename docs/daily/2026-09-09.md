# 2026-09-09 — v3 P16 (갭 감지기 계산 기반 전환 + resume 안내)

배경: P14/P15 사이 test20 계정의 프로덕션 DB를 직접 읽어, `hasEpisode=true`
인데 실제로는 안내문/빈 내용뿐인 Episode가 갭 감지기를 영구히 막고 있던
사례 5건을 발견·정리했다(고등학교 1966·대학교 1969·군 입대(period)는
Episode+UserMemory 삭제 후 `hasEpisode=false`, 결혼의 junk 2건은 삭제만).
그 정리를 하면서 짚었던 구조적 문제 — "hasEpisode 플래그가 실질 내용 여부와
분리돼 있어 저장 로직에 어떤 버그가 있든 조용히 영구 봉인될 수 있다" —를
이번에 고친다.

## P16-1. 갭 감지기 — hasEpisode 플래그 대신 실질 Episode 존재로 판단

- `lib/episode-text.ts` — `isSubstantiveEpisodeContent(content)` 추가.
  빈 문자열이거나 P14-1 `isSummaryGuidance` 패턴이면 실질 아님. 같은 판정
  함수를 재사용(핸드오프 지시 그대로) — 새 규칙을 또 만들지 않는다.
- `lib/gap-detector.ts` — 세 갭 타입 전부 전환:
  - **episode** 갭: `!e.hasEpisode` → `!e.episodes.some(isSubstantive)`.
    이벤트에 붙은 Episode 를 (기존 isPeriod 필터 없이) 전부 가져와 판단.
  - **time_gap**(period) 갭: `periodResolvedEventIds` 계산을
    `episodes.length>0`(isPeriod 필터만) → `episodes.some(ep => ep.isPeriod
    && isSubstantive(ep.content))`.
  - **person_episode** 갭: Person 의 `episodes: {take:1}` → 전부 가져와
    `episodes.some(isSubstantive)`.
- `hasEpisode` 플래그 자체는 손대지 않음(story-review 등 "이야기 있음"
  배지 표시용으로 그대로 유지) — 갭 판단에서만 분리. 핸드오프 지시대로
  "배지는 있음인데 갭 카드도 뜨는" 상태를 의도적으로 허용(빈 이야기를
  채울 기회로 본다).
- 알려진 한계(문서화, 조치 안 함): `isSummaryGuidance` 는 휴리스틱이라
  "-습니다"체 정상 회상을 간혹 오탐한다(운영 데이터 실측 — test11 계정의
  고등학교 이벤트 1건, `db/check-episode-integrity.ts` 결과 참고). 이
  경우의 부작용은 "이미 답한 이벤트가 갭 카드로 다시 뜸" 정도 — 예전처럼
  빈 내용이 영구히 막히는 것보다 안전한 방향(오탐이 미탐보다 안전, P8-2
  와 같은 원칙)으로 판단해 그대로 재사용했다.

## P16-2. EPISODE/PERSON resume 안내 문구 (+ 리팩터)

- `lib/episode-text.ts` — `buildResumeAnnouncement(label)` (`"아까 {라벨}
  이야기 이어서 들을게요."`) + `lastNonResumeAssistantText(loaded)` 추가.
  후자는 반복 재진입(답 없이 새로고침을 여러 번) 시 로그 끝이 매번 이
  안내문 자신이 되는 걸 감안해, 안내문을 건너뛰고 그 위의 "진짜 답을
  기다리던 질문"을 찾는다 — 안 그러면 재이어받기의 컨텍스트 앵커 텍스트가
  원래 질문 대신 우리 자신의 안내문으로 바뀐다.
- `ChatV3Client.tryResumePendingContext` — PERSON/EPISODE 양쪽 resume
  경로 끝에 `addBot(buildResumeAnnouncement(label))` 호출. 라벨은 인물이
  확정돼 있으면(person_episode 재진입) 그 인물 호칭, period 대화였으면
  "~이후" 문구, 아니면 이벤트 라벨. dedup 은 별도 장치 없이 addBot 의
  기존 연속-중복 방지(`lastMessageRef.current.text === text`)로 충분 —
  로그가 안 바뀐 채 재진입을 반복하면 이전 안내문과 텍스트가 똑같아 자동
  스킵된다.
- **리팩터**: `lib/person-honorific.ts` 에 조사 없는 라벨(`buildPersonLabel`)
  을 새로 뽑아야 해서 내부를 `resolvePersonLabel(name, relation) →
  {label, hasHonorific}` 로 정리하고 `buildPersonAddress`/`buildPersonLabel`
  둘 다 이걸 공유하게 바꿨다. 첫 시도는 `label === name` 문자열 비교로
  "호칭 없음"을 판단했는데, "이름 없이 호칭만"(P12-3 — `name` 자리에
  `relation` 값이 그대로 들어온 경우, 예: `name="선임"`) 케이스에서 라벨이
  우연히 `name` 과 같아져 조사가 잘못 붙는 회귀를 만들었다(`test-p11.ts`
  가 바로 잡아냄 — "선임과" 기대인데 "선임이랑"이 나옴). `hasHonorific`
  불리언을 명시로 들고 다니는 쪽으로 고쳐 해결.
