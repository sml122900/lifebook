# Lifebook 기억 에이전트 — 연구 트랙 R1~R4

> **목표**: 사용자 기억을 검색 가능한 "기억 카드"로 색인(L1) → 그 위에 자기 모델 가설(L2) → 근거 인용이 필수인 질의응답 에이전트(L3).
> **"학습" = 색인·검색이다.** 파인튜닝·모델 학습은 절대 하지 않는다. AI 는 기억을 창작하지 않고, 원본에서 고르고 정리하고 인용만 한다(북극성 "AI는 사건을 창작하지 않는다"의 연장).
> **성격**: 운영 기능이 아닌 연구 트랙. `/lab/memory` 하위에 격리하고, 허용 목록 계정(운영자 본인 + 가상 페르소나)만 대상으로 한다.

### 1-3. 원본 수정·삭제 지점

서버 액션·라우트 약 30개, 쓰기 지점 40곳 이상. Prisma `$extends`·미들웨어 없음. `updateMany`/`deleteMany`(바뀐 행 미반환)와 캐스케이드·SetNull(예: Person 삭제 → `Episode.personId` null, 탈퇴 캐스케이드)이 코드에 드러나지 않는다. → **트리거 대신 해시 비교 동기화**의 근거(§2-2).

### 1-4. 운영 코드의 Voyage 전송 경로 (추가 B, 조사만)

- **UserMemory·Episode·LifeEvent·OnboardingChatMessage 등 사용자 기록을 Voyage 로 보내는 운영 경로는 없다.**
- Voyage 호출은 `lib/embeddings.ts` 하나로 모이고, 앱 코드의 유일한 호출자는 `lib/triggers.ts` `getMusicTriggersForUser()` 다.
  - 보내는 데이터: `"{User.birthYear}년생. 관심 분야: {LifeProfile.interests}. 좋아하는 음악: {LifeProfile.favMusic}"` 한 문장(`buildUserMusicProfile`).
  - 그 호출자는 `app/timeline/page.tsx` 의 `_TimelinePageArchived` 뿐이고, 이 라우트의 default export 는 `redirect("/life-timeline")`(2026-07-01 archive) → **현재 실행되지 않는다**.
- 그 밖의 호출은 개발 스크립트다: `db/seed-music-triggers.ts`(음악 시드 카탈로그), `db/test-voyage.ts`·`db/test-rag.ts`·`db/test-trigger-failure.ts`(합성 입력).
- 따라서 처리방침 v1.0(국외 이전 대상 Anthropic 만 기재)과 **현재 운영 동작은 불일치 상태가 아니다.**

## 2. L1 — 기억 카드

### 2-1. 스키마 (R1 마이그레이션)

```prisma
// 원본 1건의 색인 원장. 카드 0장(EMPTY)이어도 행을 남겨 재추출을 막는다.
model MemorySourceUnit {
  id, userId(→User Cascade)
  sourceType       String   // EPISODE|SKELETON_EVENT|LIFE_EVENT_MEMORY|ERA_MEMORY|PHOTO_MEMORY|PERSON_MEMO|PROFILE (R4 +COMPANION_SESSION|FREE_RECORDING|CHAT_V3_DAY)
  sourceId         String   // 원본 행 id (PROFILE=userId, CHAT_V3_DAY="YYYY-MM-DD")
  sourceHash       String   // sha256(정규화 본문 + 메타[연도·인물 id·장소·isDraft] + extractorVersion)
  contextHash      String?  // 출생연도 + 골격 연도 — 바뀌면 파생 연도만 재계산(LLM 0)
  status           String   // ACTIVE|GONE|EMPTY
  extractorVersion, lastSyncedAt, lastError?, createdAt
  @@unique([userId, sourceType, sourceId])
}

model MemoryCard {
  id, userId(→User Cascade), unitId(→MemorySourceUnit Cascade)
  sourceType, sourceId      // 비정규화(인용 표시·생존 확인)
  ordinal Int               // 원본 안 순번
  kind String               // EVENT|FACT|PREFERENCE|FEELING|ROUTINE|RELATION
  summary String            // 3인칭 정리문, 주어 "화자"
  quote?, quoteField?, quoteStart?, quoteEnd?   // 원문 연속 구간(코드 검증)
  yearFrom?, yearTo?, month?
  timePrecision String      // MONTH|YEAR|RANGE|UNKNOWN
  timeBasis String          // SOURCE_FIELD|SKELETON|AGE_EXPR|ERA|NONE
  timeExpression?, lifeStage?
  personIds String[], personMentions String[], placeNames String[], keywords String[]
  sessionKey String         // KST 날짜 기반(§4)
  embedding Unsupported("vector(1024)")?, embeddingModel?
  extractorModel, extractorVersion, createdAt
  @@unique([unitId, ordinal])
  @@index([userId, yearFrom])
}

model LabUsage {            // 원가 원장 — 월 예산 가드의 근거
  id, userId?(→User SetNull, 삭제 후에도 원가 합계 보존)
  purpose String            // EXTRACT|EMBED|CONSOLIDATE|AGENT|JUDGE
  model, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens
  costMicroUsd Int, refId?, createdAt
  @@index([createdAt])
}
```

- `sourceType`·`kind`·`domain` 은 연구 중 값이 늘 수 있어 String + TS 상수(`createdVia` 관례). 상태 머신은 enum.
- ANN·GIN 인덱스는 두지 않는다. 모든 쿼리가 `userId` 범위이고 사용자당 카드 수백 장 → 전수 스캔으로 충분(`Event` 결정과 같은 논리). 사용자당 5만 장 초과 시 재검토.
- `duplicateOfId`(교차 원본 중복 묶음)는 R4 마이그레이션에서 추가.

### 2-2. 동기화 — 필요할 때 끌어오기(해시 비교), 트리거 아님

트리거를 버린 이유: ① 앱 레벨 훅은 서버 액션 30여 개 수정(격리 위반, 한 곳 누락 시 조용히 stale) ② DB 트리거는 기존 테이블 DDL(금지) ③ 캐스케이드·SetNull 은 앱 코드에 안 보여 훅으로 못 잡음 ④ 대상 몇 명 × 원본 수백 행이라 전수 해시 비교가 LLM 0회로 1초 안.

- `diffSources(userId)`: 원본 전체 → 해시 → 신규·변경(추출), 소멸(Unit GONE + 카드 삭제).
- **조회 시점 생존 확인**: 검색 결과 카드의 원본 존재·비초안 여부를 원본 테이블에 묶음 조회 → 없으면 제외. 동기화 지연과 무관하게 지운 기억은 인용되지 않는다.
- 반영 지연 완화: /lab 진입 시 "변경 N건" 표시 + 버튼. 질의 전 자동 diff(LLM 0) 후 5건 이하면 바로 추출.
- 골격 연도 변경 → `contextHash` 변화 → 파생 연도 카드만 LLM 없이 재계산.

### 2-3. 추출

| 원본 | 카드 | 방식 |
|---|---|---|
| 골격 CONFIRMED·CORRECTED | 1 | 규칙(LLM 0): "화자는 1985년 국민학교에 입학했다" |
| PROFILE, Person `metYear` | 필드당 1 | 규칙 |
| life_event | 짧으면 1, 길면 ≤6 | LLM. `content` 비면 제목·연도 규칙 카드 |
| Episode | 1~4 | LLM. 인용은 `rawTranscript` `[본인]` 줄에서만 |
| era_event·photo caption·Person memo | 1~2 | LLM. 시대 사건은 맥락으로만 |
| R4 긴 원문 | 1,500자 청크당 N | 기존 `redactTranscript`(S1) 통과 입력만 |

- 출력은 tool 스키마 강제(구조화). 창작 금지, 3인칭 "화자" 1~2문장, 인용은 원문 그대로 120자 이하.
- **모델은 연도를 계산하지 않는다** — 시기 표현(`timeExpression`)만 뽑고 연도는 결정적 해석기(§3)가 변환.
- 인물은 호칭 문자열만 받고 **코드가 Person 과 연결**(목록을 프롬프트에 넣지 않음 — S2 실측의 과억제 교훈).
- 타인의 독립 사건을 화자 사건으로 만들지 않음(S3), 타인의 건강·정치·종교 정보는 카드화 금지, 동반자 질문은 카드 아님.
- 인용 검증: 정규화 후 원문 부분문자열 확인 → 실패 시 1회 재시도 → 그래도 실패면 그 카드는 **저장하지 않고** 로그.
- `EXTRACTOR_VERSION` 을 올리면 해시가 바뀌어 전체 재추출.
- 중복 방지 3층: ① 파생 복제본 원본 제외 ② 같은 원본 안 코사인 ≥0.93 버림 ③ (R4) 원본 사이 코사인 ≥0.92 + 연도·인물 겹침 → `duplicateOfId` 로 묶음(삭제 아님 — 다른 세션의 반복 언급은 L2 근거 강도). 임계값은 평가로 보정할 가설값.

## 3. 검색 + 시기 해석

- 한 SQL: `userId` 범위 강제 필터(활성 Unit, 연도 범위 겹침 — 연도 모름은 포함하되 순위 불이익, `personIds &&`, `kind`) + 벡터(`1 - (embedding <=> q)`) + 키워드(`keywords[]` 교집합 + `summary ILIKE` 보조, `pg_trgm` 미설치 유지) → **RRF(k=60)** 합산.
- `resolvePeriod(expr, ctx)` — 순수 함수 규칙표, LLM 0. 본인 기록 1순위, 없으면 출생연도 기본값(`precision=RANGE`, "추정" 표기). 출생연도 우선순위: `OnboardingProfile.birthYear` → `User.birthYear` → v2 BIRTH → v3 BIRTH.

| 표현 | 1순위(본인 기록) | 2순위(기본값) |
|---|---|---|
| 국민학교·초등학교 때 | 골격 ELEM_SCHOOL Y → Y..Y+5 / v2 ELEMENTARY | 출생+7..+12 (`lib/age.ts` `schoolYearsForCategory`) |
| 중·고·대학 | 골격 입학년부터 | 13–15 / 16–18 / 19–22세 |
| 군대 있을 때 | MILITARY Y → Y..Y+2 (v2 `endYear` 우선) | 출생+20..+22 "입대 기록 없음 — 추정" |
| 결혼 전·후, 신혼 | MARRIAGE·RELATIONSHIP Y 기준 | 해석 불가 |
| 스무 살 때 | – | 출생+N-2..출생+N (세는 나이·만 나이 모두) |
| 국민학교 3학년 | 입학년+2 | 출생+9 |
| 80년대 / 85년쯤 | 1980..1989 / 1984..1986 | |
| IMF 때 등 | MonthEvent 제목 매칭(읽기 전용) | |

- 구현(`lib/lab/period.ts`, R1-4): 위 표 + 학교 입학·졸업/입대·제대/입사 → 해당 한 해, "80년대 초·중·말", "만 N세", 한글 나이("열일곱 살"·"서른 무렵"), "N0대", "어릴 때"(출생~12세). 여러 단계가 섞이거나("국민학교 동창이랑 군대 갔을 때") 시대 사건이 3년 넘게 퍼지면("올림픽 때") 해석 불가로 돌려 에이전트가 나눠 묻게 한다. 결과 `basis` = NUMERIC|AGE_EXPR|SKELETON|DEFAULT_AGE|ERA (DEFAULT_AGE 는 note 에 "추정").
- 골격 학교·군 복무에 붙은 Episode 는 카드 연도를 그 기간 전체(예: 고교 입학 Y → Y..Y+2)로 둔다.
- 같은 함수를 추출(카드 `timeExpression`)과 에이전트 도구(`resolve_period`) 양쪽에서 쓴다. 실패 시 "해석 불가" → 시기 필터 없이 검색.

## 4. L2 — 자기 모델 (R3)

```prisma
enum HypothesisStatus { CANDIDATE PROPOSED CONFIRMED REJECTED EDITED RETIRED }
enum EvidenceStance   { SUPPORT COUNTER }

model Hypothesis {
  id, userId(→User Cascade)
  domain String             // LIKE|DISLIKE|STRENGTH|STRUGGLE|VALUE|RHYTHM
  statement String          // 모델 원문(3인칭)
  userText String?          // EDITED — 유효 문장 = userText ?? statement
  status HypothesisStatus @default(CANDIDATE)
  supersededById String?    // 모델 상태끼리만
  statementEmbedding vector(1024)?
  supportSessions Int, counterSessions Int   // 내부 캐시, 화면 미노출
  needsRecheck Boolean      // 사용자 확정 가설의 근거 소멸·반대 누적 → 재확인 제안만
  decidedAt?, createdAt, updatedAt
  @@index([userId, status])
}
HypothesisEvidence { hypothesisId(Cascade), cardId(→MemoryCard Cascade), stance, sessionKey, rationale?, runId?  @@unique([hypothesisId, cardId]) }
HypothesisChange   { hypothesisId(Cascade), actor MODEL|USER|SYSTEM, fromStatus?, toStatus?, beforeText?, afterText?, reason, runId?, cardIdSnapshot? }  // 추가 전용
ConsolidationRun   { userId, status RUNNING|DONE|FAILED, watermark(카드 createdAt), model, 토큰(in/out/cacheRead), cardsConsidered, created/updated/retired/blocked 수, error?, startedAt, finishedAt? }
```

규칙:
1. **세션 = KST 날짜.** `OnboardingChatMessage.sessionId` 는 화면 마운트마다 새 uuid 라 새로고침만 해도 바뀌어 못 쓴다. 서로 다른 날 = 독립된 기회. 하루 몰아 한 온보딩은 PROPOSED 가 안 되는 것이 의도.
2. **PROPOSED** = 지지 세션 ≥2 AND 반대 없음(반대가 있으면 지지 세션 ≥ 반대 세션 + 2).
3. 모델이 바꿀 수 있는 상태는 CANDIDATE·PROPOSED 뿐. **CONFIRMED·EDITED·REJECTED 는 사용자만** 바꾼다.
4. **자동 RETIRED 는 모델 상태에만.** 사용자 확정 가설은 근거가 사라지거나 반대가 쌓여도 상태 유지 + `needsRecheck=true` → "근거가 된 기록이 지워졌어요 — 그대로 둘까요?"(사용자의 확인 자체가 근거).
5. REJECTED = "원래 틀린 추론"(재제안 차단). RETIRED = "한때 맞았지만 지금은 아님"(사용자 버튼 "예전엔 그랬어요"로도 진입).
6. 재제안 차단은 코드에서: `statementEmbedding` 코사인 ≥0.88 이면 막고 Run 에 blocked 로 계수.
7. **민감정보 차단**: 건강 상태·종교·정치·성적 지향 가설 금지(프롬프트 + 코드 키워드 필터). STRUGGLE 은 비의료적인 것만. 주어는 화자만(타인 가설 금지).
8. 신뢰도 숫자는 **두지 않는다**(세션 수만 내부 캐시).

통합 절차: 워터마크 이후 새 카드 30장씩 → 활성 가설 목록과 함께 Sonnet(tool 스키마: 기존 가설 id 별 지지/반대, 새 후보) → 코드가 id 검증·REJECTED 유사·민감 차단 → 근거 멱등 upsert → 세션 재계수 → 상태 규칙 → Change 기록. 사용자당 RUNNING 1건(`updateMany` 선점). 새 카드 0장이면 LLM 0회.

## 5. L3 — 에이전트 (R2)

```ts

  → { ok: true, yearFrom, yearTo, precision, basis, note? } | { ok: false, reason }
search_memories({ query, keywords?, yearFrom?, yearTo?, personIds?, kinds?, limit? /*기본 8, 최대 10*/ })
  → { cards: CardHit[] }   // CardHit = { cardId, summary, when, people, places, kind, sourceType, quote?(≤80자), mentions }

```

```ts
AnswerPayload = {
  claims: { text, cardIds: string[], hypothesisIds?: string[] }[],
  conflicts?: { topic, cardIds: string[] }[],          // 서로 다른 기록은 둘 다
  noRecord?: { topic, followUpQuestion: string },
}
```

- 서버 검증: `cardIds` 는 이번 실행에서 도구가 실제로 돌려준, 아직 살아 있는 카드여야 한다. 아니면 주장 폐기·계수. 전부 폐기되면 noRecord.
- 표기: 인용 "…들려주셨어요 [c12]" / 기록 없음 "아직 들려주신 적 없는 이야기예요. 혹시 …?" / 모순 "…라고 하신 기록[c3]도, …라고 하신 기록[c21]도 있어요. 어느 쪽이 맞을까요?"
- 규칙: 연도 직접 계산 금지(`resolve_period`), 골격 UNCONFIRMED 를 사실로 말하지 않기, 가설은 상태별 표현(CONFIRMED "직접 확인해 주신", PROPOSED "그런 것 같다는 기록이 있어요"), 민감 추론 금지, 도구 최대 6라운드.

## 9. 마이그레이션 절차 (단계마다)

1. `schema.prisma` 에 신규 모델·enum + User 역참조 필드(관계 필드만) → `npx prisma format` → `npx prisma validate`.
2. `npx prisma migrate status` 로 대기 중인 다른 마이그 없음 확인.
3. `npx prisma migrate diff --from-config-datasource prisma.config.ts --to-schema prisma/schema.prisma --script` (shadow DB 없음 — 운영 DB 읽기만).
4. 신규 관련 문장만 `prisma/migrations/<ts>_lab_memory_rN/migration.sql` 로 옮긴다. **drift 4건 제외**, grep 으로 `DROP`·`ALTER TABLE "User"`·기존 테이블명 0건 확인, vector 타입 표기 확인.
5. **SQL 전문 + "User 테이블 대상 DDL 0건" 명시 보고 → 성민 승인.**
6. `npx prisma migrate deploy` → `prisma generate` → migrate diff 재실행으로 drift 4건만 남았는지 확인. dev 서버가 떠 있었으면 재시작.
7. `migrate dev` 금지. 빌드 전 dev 서버 종료. 일지 기록.
