# 트랜잭션 시간 초과(P2028) — 왕복 수·트리거·서버 실행 시간이 아니라 Postgres 밖에서 멈춤(어디인지는 아직 못 가름)

## 문제 상황

38분(회귀 22종 3번) 동안 `P2028` 0건 — 5초 넘는 멈춤은 재현되지 않았다. 처음 26분은 400ms 넘은 것 0건이고, 마지막 12분에 25건이 나왔다.

- **DB 쪽만 느려진 구간(2026-11-07 01:53~01:57 KST, 약 3.5분):** 왕복이 67ms → 약 150ms. 풀러 트랜잭션 최대 534ms · 새 연결 최대 938ms · 세션 연결 최대 255ms.
- 같은 시간 바깥 TCP 는 최대 50ms 그대로, 타이머 밀림 최대 16ms. 그 구간 회귀도 느려졌다(`test-my-life-edit` 149 → 174초, `test-node-body` 78 → 110초).

확인한 것은 여기까지다.

- 멈춤은 Postgres 밖이다. 이 PC 와 VPN 첫 구간도 아니다(바깥 TCP·타이머가 그대로).
- 남은 곳은 VPN 출구 ↔ 서울 구간과 풀러(Supavisor)다. DB 두 연결 모두 같은 풀러 주소라 이 측정으로는 가르지 못한다. 잡힌 것도 왕복 2배이지 5초 멈춤이 아니다.
- 가르는 방법: VPN 을 끄고 같은 감시·회귀를 돌린다. 끈 상태에서도 느려지는 구간이 나오면 풀러 쪽이다.

## 운영에서 생길 수 있나

**5초를 넘길 가능성은 낮다고 본다. 다만 풀러 쪽 원인이면 운영에도 닿으므로 없다고 할 수 없다.**

- 운영 함수는 `icn1`(응답 머리글 `X-Vercel-Id` 확인), DB 풀러는 `ap-northeast-2` — 같은 서울이고 VPN 이 없다. 같은 리전 왕복은 수 ms 라 보고(운영에서 직접 재지는 않음) `deleteAccountTx` 는 0.1초 안쪽 예상이다.
- 왕복 수·트리거·서버 실행 시간이 원인이 아니므로 데이터가 늘어도 이 원인으로는 안 생긴다.
- 경로가 원인이면 운영에는 없다. 풀러가 원인이면 운영에서도 난다 — 위 측정으로는 어느 쪽인지 모른다.
- 나더라도 트랜잭션이 통째로 되돌아가고 화면에 저장 실패가 뜬다. 다시 하면 된다(반쯤 저장되는 일 없음).

## 조치

**코드 변경 없음.**

- 왕복을 줄여도 고쳐지지 않는다 — 앞쪽 문장에서 멈추기 때문이다.
- 제한(5초)을 늘리면 회귀는 덜 깨지지만, 멈춘 트랜잭션이 잠금을 더 오래 쥔다. 운영 근거가 없어 늘리지 않는다.

회귀에서 다시 나면: 로그에서 `P2028` 을 확인하고 그 스크립트만 다시 돌린다. `test-*` 의 정리(`finally`)가 함께 실패하면 원래 오류가 가려져 정리 쪽 오류만 보인다.
