## 0. 요약

- **추천은 안 C다(§2).** 기존 6종(`LIFE_EVENT`·`EPISODE`·`PERSON_GROUP`·`PERSON`·`PLACE_GROUP`·`PLACE`)과 그 원본 테이블은 손대지 않는다. 사용자 카테고리·묶음·항목은 새 테이블 **`CustomNode` 하나**에 부모-자식으로 담는다. 깊이는 카테고리 → 묶음 → 항목, 최대 2다. `NodeType` 에는 `CUSTOM` 하나를 **맨 뒤(가장 낮은 순위)** 에 더하므로 방향 CHECK 식은 바꾸지 않는다. 정리 트리거는 하나 더한다. 이관할 행은 0이다.
- **이유는 의존 조사(§1)에서 나왔다.** 포스터 브릿지·인터뷰·갭·연구실·확인질문·자유 대화는 모두 "시기·이야기·사람" 세 원본만 안다. 사용자 노드를 그 세 테이블에 섞지만 않으면 이 영역들은 영향이 0이다. 반대로 사용자 카테고리를 직접 만든 시기(CUSTOM `LifeEvent`)로 흉내 내면, 포스터 행·연도 문항·"○○ 시절" 갭·확인질문 연도 이동에 휘말린다.
- **같은 단계에서 반드시 고쳐야 할 곳이 하나 있다.** 정합 점검의 `ownerOf`(`lib/node-graph-reconcile.ts:53-65`)는 6종을 CASE 로 하드코딩한다. 새 종류의 노드는 주인이 NULL 로 나오고, 그러면 `--apply` 정리(`:182-186`)가 그 노드의 연결과 본문을 **실제로 지운다**. 그래서 `ownerOf` 는 마이그와 같은 커밋에서 고친다.
- **지도(§3).** 사용자 카테고리마다 오른쪽 열 장소록 아래에 영역을 하나씩 만든다. 영역은 기존 `layoutRegion`(`lib/my-life-layout.ts:461`)을 그대로 쓴다(인물록·장소록이 이미 같은 함수). 카테고리 20개·노드 300개 기준으로 접힘 규칙과 이동 줄 카테고리 목록을 두고, 390px 실측 통과 기준을 정했다.
- **AI 지도 편집(§4)** 은 `/my-life` 아래 시트에서 하고, 도구 11개를 쓴다. 쓰기는 모두 기존 함수를 거친다. 연결은 `saveNodeLink`, 빼기는 `removeNodeLink` 입구를 그대로 쓰고, 이름 바꾸기·합치기와 사용자 노드 함수만 새로 만든다.
  - 모델에는 실제 id 대신 별칭(n1·n2…)만 보인다.
  - 쓰기 도구는 사용자 말의 인용(`said`)을 붙여야 한다. 인용을 확인하지 못하면 바로 반영하지 않고 계획 카드로 바꾼다.
  - 지우기·합치기는 확인 카드를 거친다.
  - 결과 카드의 "한 일" 목록은 코드가 실제 실행 기록으로 만든다.
  - 1회 원가는 약 $0.007~0.038(Sonnet, §4.5)로 추정한다.
- **처리방침(§5).** 목적은 3항 "인생 기록 정리"·"AI 회상 보조" 안이지만, 열거된 기본 정보 목록 밖 항목이 생긴다(모임·묶음·직접 만든 분류의 이름, 인물 글, 지도 정리 요청). 1항 수집 항목에도 "직접 만든 분류"가 새로 생긴다. 그래서 **v1.4 개정이 2단계 배포의 선행 조건**이다(공지일 + 7일 시행, 작업 규칙 11). 업체가 그대로라 동의 버전 4는 유지한다(v1.2 선례).
- **단계(§6).** 1 데이터 층(화면 변화 0) → 2 지도(v1.4 시행 뒤 배포) → 3a 질문 답하기(그래프만) → 3b 바로 반영 도구 + 되돌리기 → 3c 지우기·합치기 확인 카드 → 3d 이야기 본문 근거 질문 → 3e(선택) 제안 카드가 사용자 노드를 제안.

### 1.3 조사 결론

1. 고칠 곳은 "종류를 직접 나열하는 곳"(§1.1)뿐이다. 다만 정합 점검 `ownerOf` 는 고치지 않으면 **데이터가 지워지는** 곳이라, 새 종류를 넣는 마이그와 같은 커밋에서 고친다.
2. 사용자 노드는 **새 테이블**에 둔다. 시기·이야기·사람 테이블에 섞지 않는다. 그러면 §1.2 전체가 영향 0이다.
3. 이 조사 중 낡은 주석 하나를 발견했다. `lib/account-deletion.ts:16-18` 의 cascade 목록 주석에 노드 테이블이 없다. 고치지 않고 기록만 남긴다.

### 2.2 추천 — 안 C, 근거

1. **§1.2 영향 0.** 시기·이야기·사람 원본에 섞지 않는다. 포스터·인터뷰·갭·연구실·확인질문·자유 대화는 코드 변경 0이다.
2. **추가만 하는 가장 작은 마이그.** 테이블 1·enum 값 1·트리거 1이다. 노드 그래프 1단계·장소 묶음 마이그와 같은 결이다(추가만, 이관 0, 기존 id 그대로).
3. **"페이지 안 페이지" = 부모 하나.** 카테고리(맨 위 행) 안에 항목이 있고, 항목이 다른 항목을 품으면 그것이 묶음이다. 카테고리·묶음·항목이 같은 테이블이라 개념이 하나다. 깊이 2 제한으로 동선이 단순하다(시니어 접근성).
4. **포함은 진짜 FK 다.** 묶음·카테고리 소속(`parentId`)은 자기 참조 FK 라 정리 트리거가 필요 없다. 트리거는 다형 연결(`NodeLink`·`NodeBody`) 정리용 1개만 둔다.
5. **배치는 재사용한다.** 항목의 `groupIds = [부모 묶음 id]`(부모가 카테고리면 빈 배열)로 바꾸면 `layoutRegion` 을 그대로 쓴다. 부모가 하나라 묶음 영역이 겹치지 않는다.
6. **B 는 사용자에게 보이는 이득이 없다.** B-2 의 진짜 FK 이득(다형 트리거 제거)은 크지만, 모든 생성 경로 이중 쓰기 위험이 더 크다. 코드에서 노드 종류 자체가 계속 늘어날 때 다시 본다.

안 C 의 약점과 대응:
- **묶음 다중 소속 불가.** 인물록 모임은 한 분이 여러 모임에 들 수 있는데(Euler), 사용자 카테고리 항목은 묶음 하나에만 든다. 겹침이 필요하면 연결(간선)로 표현한다. → Q74.
- **연도 칸 없음.** 시간은 시기와의 연결(`LIFE_EVENT>CUSTOM`)로 나타낸다. 지도에서 그 시기를 고르면 간선으로 보인다. → Q78.

### 2.3 안 C 스키마 초안 — 설계, 적용 안 함

**규칙(코드에서 지킴 — 저장 함수 한 곳, `lib/custom-node.ts` 신설 예정):**

| 깊이 | 행 | 규칙 |
|---|---|---|
| 0 | 카테고리(`parentId` 없음) | 사용자가 이름 붙임. 연결 대상이 아님(카테고리 자체를 이야기에 잇지 않음). `builtin` 행은 인물록·장소록 자리라 자식이 없고 지울 수 없음. 화면 표시 이름·영역 순서만 담음(Q76·Q77) |
| 1 | 항목 또는 묶음(부모 = 카테고리) | 자식이 있으면 묶음, 없으면 항목. 연결 가능 |
| 2 | 묶음 안 항목(부모 = 깊이 1) | 자식을 둘 수 없음. 연결 가능 |

- 부모·자식은 같은 사용자 것이어야 하고, `builtin` 행 아래에는 둘 수 없다.
- 묶음을 지우면 자식은 카테고리로 올린다. 모임을 지워도 구성원이 남는 것과 같다. 앱이 같은 트랜잭션에서 부모를 바꾼 뒤 지운다.
- 카테고리를 지우면 확인 카드를 거친 뒤 안의 것도 같이 지운다(FK Cascade — Q80).
- FK 를 Cascade 로 두는 이유가 있다. 탈퇴할 때 `userId` Cascade 로 한 사용자 행이 한꺼번에 지워지는데, 자기 참조가 RESTRICT 면 지우는 순서에 따라 막힐 수 있다.

**방향 CHECK 에 사용자 노드 순위를 두는 법 — 카테고리별 순위는 두지 않는다.**
- 순위가 하는 일은 같은 쌍을 한 행으로 만드는 **정규화뿐**이고, 뜻(무엇이 무엇을 품는가)은 담지 않는다. 카테고리는 행이라 CHECK 가 볼 수도 없다.
- `CUSTOM` 을 맨 뒤에 두면 기본 종류 ↔ 사용자 노드 연결은 늘 기본 종류가 `from` 이다. 사용자 노드끼리는 기존 "같은 종류 = id 바이트 순" 규칙을 그대로 쓴다. CHECK 식은 그대로이고 기존 행에도 영향이 없다.
- 방향에 뜻이 있는 "포함"은 `NodeLink` 가 아니라 `parentId` 에 둔다. 정규화가 부모·자식 방향을 뒤집는 문제가 그래서 생기지 않는다.

**연결 허용 쌍(`ALLOWED_PAIRS` 추가안 — Q79):** `LIFE_EVENT>CUSTOM`(그 시절의 것) · `EPISODE>CUSTOM`(이야기에 나온 것) · `PERSON>CUSTOM`(그분의 것) · `PLACE>CUSTOM`(그곳의 것) · `CUSTOM>CUSTOM`(다른 묶음·카테고리의 것끼리 "관련").
- 부모-자식 사이를 `NodeLink` 로 또 잇는 요청은 거부한다(한 쌍 = 한 곳).
- 깊이 0(카테고리) 행은 `ownsNode` 단계에서 거부한다.
- 모임·장소 묶음 ↔ 사용자 노드(`PERSON_GROUP>CUSTOM`·`PLACE_GROUP>CUSTOM`)는 1차에 넣지 않는다.

**포함(넣기·빼기)의 입구:**
- 모임·장소 묶음(다중 소속)은 지금처럼 `saveNodeLink`/`removeNodeLink`(`ROUTED_PAIRS`)를 쓴다.
- 사용자 노드 묶음(부모 하나)은 부모를 바꾸는 함수 `moveCustomNode` 를 새로 둔다. 이야기의 주 소속 시기(`Episode.lifeEventId`, 부모 하나)를 `saveNodeLink` 가 아닌 `moveEpisodeToLifeEvent`(`lib/episode-move.ts:51`)로 바꾸는 것과 같은 구분이다. 정리하면 부모가 하나인 포함 = 옮기기 함수, 여럿인 포함·연결 = `saveNodeLink`.

**같은 커밋에서 고칠 것(1단계):** `NODE_RANK` · `ALLOWED_PAIRS` · `ownsNode` · **`ownerOf`(정합 점검)** · `test-node-graph` ①(트리거 8개, 순위 7개) · 정합 점검 14(깊이 3 이상, 부모가 남의 것, `builtin` 아래 자식, 카테고리에 걸린 연결) · `test-withdrawal` 시나리오 6 집계 칸.

### 2.4 안 A·B 를 고르지 않는 이유(요약)

- **A:** 개념이 4개(카테고리·노드·묶음·구성원)이고 enum 도 2개 는다. 다중 소속 일관성(인물록 모임과 같은 동작)이 얻는 것인데, 사용자 카테고리에서 겹치는 묶음이 필요하다는 근거가 아직 없다. Q74 가 "다중"으로 결정되면 A-1 로 바꾼다. 그 경우 바뀌는 것은 `CustomGroup`·`CustomGroupMember` 추가와 `ROUTED_PAIRS` 1쌍뿐이고, 배치는 이미 Euler 를 지원한다.
- **B:** B-1 은 타입 있는 FK 와 §1.2 소비자 전부를 깬다. B-2 는 생성 경로 전부의 이중 쓰기가 필요하다. 이관 노드 331·연결 92행이고 실고객 행도 따로 있다. 사용자에게 보이는 이득은 없다.

### 3.1 영역 규칙

## 4. AI 지도 편집

### 4.1 위치와 경계

- **`/my-life` 아래 시트에서 연다.** 버튼은 `[문구 필요: AI에게 부탁하기]` 다. 지도 바로 옆에서 결과가 보이고, 바뀐 노드로 지도가 간다. 구현 때 `docs/navigation-map.md` 를 갱신한다(작업 규칙 7, Q84).
- **자유 대화(`/chat-v3`, 회상)에는 쓰기 도구를 주지 않는다.** 이야기에서 찾아낸 것은 지금처럼 제안 카드로 낸다. 정리하면 "시킨 일 = 지도 편집 시트", "찾아낸 것 = 제안 카드".
- 이 시트의 AI 도 이야기에서 찾아낸 것은 실행하지 않는다. "이것도 할까요?" 제안 줄만 내고, 누르면 계획 카드로 간다.

- **한 명령은 여러 단계다.** 기존 함수가 각자 트랜잭션을 가지므로 단계마다 원자적이고 명령 전체로는 원자적이지 않다. 중간에 실패하면 "한 일"에 성공한 것만 남고 그것을 되돌릴 수 있다.

## 5. 처리방침 영향

현행은 처리방침 **v1.3**(2026-11-03 시행), `POLICY_NOTICES` 빈 배열(첫 사용 v1.4부터), 동의 버전 4다.
- 3항 Anthropic 항목 원문(`app/privacy/page.tsx:38`): "AI 기능 이용 시 입력하신 대화·회상 내용, 녹음을 변환한 텍스트, 답변 품질을 위해 함께 전달하는 기본 정보(출생연도·지역, 인물 이름·관계, 장소 이름, 대화 중 답하신 내용)"
- 3항 목적: "AI 회상 보조·문장 다듬기·인생 기록 정리·포스터 문장 생성"
- 동의 문구(`app/consent/ConsentChecklist.tsx:30-34`)는 업체·용도만 적고 항목은 3항으로 넘긴다.

| 새로 AI(Anthropic)로 가는 것 | 3항 범위 |
|---|---|
| 지도 정리 요청·질문 문장 | "입력하신 대화" 안으로 볼 수 있으나 명시 권장 |
| 시기 이름·연도, 사람 이름·관계, 장소 이름 | 이미 목록 안(제안 카드가 보냄) |
| 모임·장소 묶음 이름, **직접 만든 분류(카테고리)·묶음·항목 이름과 메모** | **목록 밖** |
| 이야기 제목·본문 발췌(읽기 도구) | "회상 내용" 안 |
| 인물에 대해 적은 글·메모(`NodeBody` PERSON·`Person.memo`) | **목록 밖**("인물 이름·관계"만 열거) |

**판단:** 목적은 범위 안이다. 열거된 기본 정보 목록 밖 항목이 생기므로, v1.2(장소 이름 추가) 선례처럼 항목을 더하는 개정을 추천한다. 1항 나(서비스 이용 중 입력·생성)에도 수집 항목 "직접 만든 분류"가 새로 생기므로, 사용자 카테고리를 받기 시작하는 2단계 전에 개정이 시행돼 있어야 한다.

- **Voyage(임베딩)는 이 설계 1차에서 쓰지 않으므로 영향이 없다.** 처리방침에 Voyage 가 없다는 사실(`node-graph-self.md` §5 기록)은 그대로다. 연구실 밖 운영 경로의 Voyage 호출은 없다(옛 `/timeline` 은 2026-07-01부터 redirect). 카드 색인을 운영으로 올리면 3항에 업체를 더해야 하고, 동의 문구가 업체를 열거하므로 동의 버전도 올려야 한다. 이것은 이 설계 밖이다.
- **동의 버전:** 업체·국가·목적이 그대로이므로 4를 유지한다(v1.2·v1.3 결정과 같음 — Q93).

**v1.4 초안 — 항목만, 문장은 확정 전:**

1. 1항 나 목록에 "· 직접 만든 분류: 회원님이 이름 붙인 분류와 그 안의 묶음·항목의 이름과 메모" 추가.
2. 3항 Anthropic 항목의 기본 정보 괄호에 "모임·장소 묶음·직접 만든 분류와 항목의 이름, 인물에 대해 적으신 글" 추가 + "AI에게 부탁하신 기록 정리 요청과 질문" 추가.
3. 3항 Anthropic 목적에 "기록 지도 정리·질문 답변" 추가(2항 이용 목적 문장에도 같은 말).
4. 개정 이력 "v1.4 — [시행일] 시행 (…)" + `lib/policy-notice.ts` `POLICY_NOTICES` 등록: 띠 요약 `short` `[문구 필요: 11자 이내, 기술 용어 금지]`, 상세 `detail`, 공지일, 시행일 = 공지일 + 7일(작업 규칙 11). 회귀 `test-auth` ③이 등록값·개정 이력을 확인한다.
