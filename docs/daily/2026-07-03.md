## 1. PWA 셋업 (`c665745`)

Next.js 네이티브 컨벤션만으로 구성 — 새 의존성 0.

- `app/manifest.ts` — `MetadataRoute.Manifest` 네이티브 컨벤션(자동 `<link rel="manifest">`).
- 아이콘 4종 — 기존 `favicon.ico` 안의 256px 마크(검은 원+흰 삼각형)를 `sharp` 로
  추출해 192/512/512-maskable(세이프존 65% 축소 + 브랜드 배경 패딩)/apple-icon
  (180px, 무투명) 생성. 별도 디자이너 자산 요청 없이 기존 브랜드 자산 재활용.
- `public/sw.js` — **라이브러리(next-pwa/serwist) 대신 수제**. 두 라이브러리 모두
  빌드타임 precache manifest 를 웹팩 플러그인으로 주입하는 방식이라, "배포했는데
  안 바뀜" 사고의 전형적 원인이 될 수 있다고 판단(이 프로젝트가 과거 `.next` 캐시
  stale 로 여러 번 데인 이력 — 아래 트러블슈팅 참조). ~50줄 수제 SW 는 캐싱 로직이
  전부 눈에 보여 감사 가능: `/_next/static/*`·`/icons/*` 만 cache-first(콘텐츠
  해시라 안전), 페이지·API·서버 액션·동적 데이터는 절대 가로채지 않고 항상 네트워크.
  `skipWaiting`+`clients.claim` 으로 배포 즉시 새 버전 활성화.
- `public/offline.html` — 오프라인 네비게이션 전용 폴백(어르신 친화 문구), 정적
  단일 파일이라 Next 빌드 파이프라인과 무관하게 항상 안전.
- `ServiceWorkerRegister` — 프로덕션에서만 등록(dev 는 HMR 혼란 방지로 끔).
- `layout.tsx` — `viewport` themeColor + `appleWebApp` + 구형
  `apple-mobile-web-app-capable` 메타(iOS 17.4 이전 Safari 대응 — 시니어 사용자
  다수 해당, 신형 메타만 넣으면 구형 기기에서 홈화면 추가가 standalone 으로 안 열림).

**검증**: `npm run build` 통과, `manifest.webmanifest`·아이콘·`sw.js`·`offline.html`
전부 200 확인(curl). Chrome 브라우저 자동화로 실제 SW 등록·활성·`navigator.serviceWorker.
controller` 확인, 캐시 내용 직접 조회해 정적 자산만 들어있고 페이지·API 0개인 것 확인
(배포 후 stale 우려의 핵심 검증 포인트).

## 2. 디자인 시스템 문서화 (`docs/design-system.md`)

"일반 IT 서비스 미니멀 원칙은 채택하되 토큰은 우리 것"이라는 요구를 실측으로
풀었다 — 이상론이 아니라 지금 코드가 이미 하고 있는 걸 grep 으로 관찰해 정리.

- 팔레트 9개 토큰의 WCAG 대비를 직접 계산: `ink` 14.2:1(AAA) · `ink-soft` 7.0:1(AAA)
  · `ink-faint` 5.3:1(AA, 셋 중 최저 — 남용 금지 근거).
- 타이포 실측: `text-lg`(328곳)·`text-base`(436곳)가 본문 주력, `text-sm`/`text-xs`는
  실측상으로도 대체로 캡션 전용으로 지켜지고 있었음 — "본문 최소 16px" 원칙이 이미
  대체로 지켜지고 있다는 근거 확보.
  Button.tsx 5-variant 계약(primary 화면당 1개·destructive=빨강 필 금지)을 그대로
  "이미 코드로 강제된 규칙"으로 문서화.
- 확장 의미색(emerald/amber/rose/violet/sky, 405곳)은 삭제 대상이 아니라 이미
  정착된 "의미 분리용" 레이어로 인정하고 경계만 명시(새 색 추가 금지).

## 4. UI 개선 1순위 — 위험 버튼 교정 (`5b4d294` → `7abf8cb`)

감사에서 찾은 항목 중 안전 최우선(빨강 필 삭제/탈퇴 버튼) 3건만 선별 교정.

- `DeletePersonButton.tsx`·`WithdrawForm.tsx` 확인 버튼: 필 빨강 → destructive
  아웃라인(보더+투명 배경+danger 텍스트). 취소 버튼과 같은 크기로 맞춰 "실수로
  누르기 쉬운 큰 빨강 버튼" 자체를 제거 — 위험 인지는 문구·확인단계(모달, "탈퇴"
  타이핑 게이트)로 그대로 유지.
- `EmptyState.tsx`: 손수 스타일링한 Link → `ButtonLink`. 공용 컴포넌트라
  `/life-timeline`·`/poster`·`/enter`·`/people`·`/photos` 5개 화면이 한 번에 정합.
- **트러블슈팅** — 1차 픽스 배포 직후 성민이 Chrome 에서 `WithdrawForm` 버튼이
  여전히 필 빨강으로 보인다고 재확인 요청. 소스는 이미 정확했으나, 로컬 `.next`
  디렉토리 mtime 이 수정 커밋 시각보다 앞선 것을 발견 — stale 빌드였다.
  `rm -rf .next && npm run build` 후 컴파일된 번들을 직접 grep 해 구 클래스 문자열이
  완전히 사라졌음을 증명. 같은 조사 과정에서 `life-timeline/manage/DeleteButton.tsx`
  가 `DeletePersonButton.tsx` 와 구조가 동일한 필 빨강 버튼인데 원 감사 에이전트가
  놓쳤다는 걸 발견해 함께 교정(`7abf8cb`). 상세: `docs/troubleshooting/
  stale-next-cache-false-negative.md`.

## 5. UI 개선 2순위 — ink-faint HIGH 13건 (`219d8e1`)

ink-faint 55곳 중 HIGH(가격·개인정보·핵심데이터·전역액션) 13건만 이번 배치로 교정,
나머지 42건(MEDIUM)은 다음 배치. 전부 `ink-faint`(5.3:1) → `ink-soft`(7.0:1), 위계
보존을 위해 전부 `ink` 로 올리지 않음 — 12곳 모두 더 진한 형제 요소(제목·가격·버튼)가
이미 있는 2차 정보라 ink-soft 가 적정선. 로그아웃 버튼은 "다른 메뉴보다 눈에 덜
띄게"라는 기존 코드 주석의 의도(사이드 패널)를 크기·위치는 그대로 두고 색만
가독 최소선으로 올려 보존.

검증: `text-ink-faint` 전체 개수 85→72(정확히 13개 감소, 그 외 미변경 확인). eslint 로
발견된 4건(useRef/setState-in-effect)은 `git stash` 로 변경분 제거 후 재실행해
동일하게 재현 — 이번 변경과 무관한 기존 이슈로 확인.

## 회고

- **PWA 라이브러리를 안 쓰기로 한 결정**이 이 세션 전체를 관통하는 태도와 일치한다 —
  "블랙박스 자동화보다 눈에 보이는 얇은 레이어"를 반복해서 택했다(수제 SW, 실측
  기반 디자인 문서, grep 근거 있는 감사).
- **감사(조사) 와 교정(실행) 을 별도 요청으로 분리**한 게 유효했다. 320여 건을
  한 번에 다 고치지 않고 심각도순 배치로 쪼개 매 배치 검증 가능한 단위로 유지.
- **"수정했다"는 보고를 사용자가 직접 재현해 반박**한 게 이번 세션의 핵심 교훈으로
  이어졌다 — 소스 코드가 맞다는 것과 사용자가 보는 화면이 맞다는 것은 다른
  주장이고, 후자는 빌드 아티팩트까지 내려가서 검증해야 한다.
